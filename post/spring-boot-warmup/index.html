Spring Boot 는 Ready 여도 첫 요청이 느릴 수 있다 - Warm-up 으로 지연 최소화하기

2026-11-23약 13분
#Spring#JVM#kubernetes
새 버전을 배포하면 새로 뜬 서버는 Ready 가 되면, 쿠버네티스든 로드밸런서든 앞단의 상태 확인을 거쳐 곧바로 트래픽을 받기 시작한다.
하지만, Ready 가 됐다고 해서 요청을 처리할 준비가 다 끝난 것은 아니라서, 첫 요청이 DB 나 Redis, 다른 서비스를 처음 부르는 구간에서 느려질 수 있다.
이 구간을 Ready 전에 미리 한 번 불러 두는 Warm-up 을 Spring Boot 에 직접 넣어 보고, 첫 요청과 배포 중 응답이 얼마나 달라지는지 알아보자.

Ready 인데 첫 호출이 느린 이유

Spring Boot 가 시작해서 첫 호출을 받기까지는 아래 순서로 진행된다.

빈 생성 → 웹 서버 시작 → Ready → 첫 호출 (첫 연결, 클래스 로딩)

Ready 전에 DB 나 Redis 연결, 처음 쓸 클래스까지 모두 준비해 두지는 않아서, Ready 뒤 첫 호출이 직접 처리하게 된다.

  • 첫 연결: DB 커넥션 풀(미리 만들어 두고 돌려 쓰는 연결 묶음)은 시작할 때 DB 를 쓰는 곳이 없으면 첫 조회 때 만들어지고, Redis 나 다른 서비스 API 도 처음 부를 때 네트워크 연결을 맺는다.
  • 클래스 로딩: JVM 은 클래스를 처음 쓸 때 파일에서 읽어 메모리에 올리는데, 처음 지나가는 API 경로의 클래스가 이때 한꺼번에 올라온다.

이 두 가지는 한 번 하고 나면 끝나는 일이라서, Ready 전에 한 번만 불러 두면 첫 호출에서 빠진다.
자주 불리는 코드를 기계어로 바꿔 빠르게 만드는 JIT 컴파일도 있지만, 같은 코드가 수백에서 수천 번 불려야 진행되기 때문에, Warm-up 은 한 번 호출로 끝나는 첫 연결과 클래스 로딩을 주로 대상으로 한다.

Warm-up 이 없을 때와 있을 때, 시작 과정에서 어디서 처리되는지 그려 보면 아래와 같다.

빠르게 적용하기

가장 단순한 방법은 서버가 시작할 때 한 번 실행되는 ApplicationRunner 에서, 느린 구간이 있는 자기 API 를 한 번씩 호출해 두는 것이다.

java
@Component
class WarmupRunner implements ApplicationRunner {

    private final RestClient.Builder restClientBuilder;

    private final Environment environment;

    private final WarmupProperties properties;

    ...

    @Override
    public void run(ApplicationArguments args) {
        // 포트는 웹 서버가 뜬 뒤에 정해져서, 생성자가 아니라 여기서 읽는다
        String port = this.environment.getRequiredProperty("local.server.port");
        RestClient client = this.restClientBuilder.baseUrl("http://localhost:" + port)
            .requestFactory(requestFactory(this.properties.timeout()))   // 요청마다 제한 시간
            .build();
        // 설정한 조회 API 를 Ready 전에 한 번씩 부른다
        for (String path : this.properties.paths()) {
            try {
                client.get().uri(path).retrieve().toBodilessEntity();
            }
            catch (RuntimeException ex) {
                // 다른 서비스가 잠깐 느린 것만으로 시작이 실패하지 않게, 로그만 남기고 넘어간다
                log.warn("[warmup] {} 실패: {}", path, ex.getMessage());
            }
        }
    }
}
yaml
warmup:
  paths:
    - /users/1      # DB 를 조회하는 API
    - /products/1   # Redis 를 조회하는 API
    - /external     # 다른 서비스 API 를 부르는 API
  timeout: 2s

꼭 미리 불러야 하는 경로는 실패할 때 예외를 던져 시작을 멈추는 편이 좋다.

Warm-up 경로 고르기
모든 API 를 넣기보다, 첫 호출이 느린 경로를 골라 넣는 편이 좋다.
첫째, 외부 호출이 있는 경로다. DB, Redis, 다른 서비스 API 는 첫 요청 때 연결을 맺는다.
둘째, 처음 지나갈 때 무거운 경로다. 로그인처럼 처음 올라오는 클래스가 많거나, 응답이 커서 JSON 변환이 무거운 경로가 그렇다.
더 읽어 보기
✔ 커넥션 풀과 타임아웃
✔ Redis 연결과 DNS
✔ HTTP 클라이언트 커넥션 풀

Warm-up 의 동작

1) 코드가 실행되는 흐름

코드는 짧지만, Spring Boot 가 시작하는 순서와 맞물려서 동작하는데, 그 흐름을 그려 보면 아래와 같다.

Warm-up 1회로 띄운 서버의 로그를 보면, 이 순서가 그대로 찍혀 있다.

text
13:48:15.129 INFO  [main]            Tomcat started on port 8080 (http)
13:48:15.137 INFO  [main]            Started WarmupApplication in 2.22 seconds
13:48:15.242 INFO  [nio-8080-exec-2] Initializing Servlet 'dispatcherServlet'
13:48:15.313 INFO  [nio-8080-exec-3] HikariPool-1 - Starting...
13:48:15.497 INFO  [nio-8080-exec-3] HikariPool-1 - Start completed.
13:48:15.814 INFO  [main]            [warmup] HTTP 모드 1번, 630ms, 실패 0건
13:48:15.815 DEBUG [main]            Application availability state ReadinessState changed to ACCEPTING_TRAFFIC

먼저 웹 서버가 포트를 열고 Started 가 된 뒤에, Spring Boot 가 main 스레드에서 ApplicationRunner 를 부른다.
포트 번호는 웹 서버가 뜬 뒤에야 정해지기 때문에, 코드에서도 생성자가 아니라 run 안에서 local.server.port 를 읽는다.

Runner 가 localhost 로 보낸 요청은, 밖에서 온 요청과 똑같이 Tomcat 의 요청 처리 스레드(nio-8080-exec)가 받는다.
DispatcherServlet 초기화와 커넥션 풀 생성이 main 이 아닌 nio-8080-exec 스레드에 찍히고, 필터와 컨트롤러, JSON 변환까지 실제 요청과 같은 길을 한 번 지나간다.

이 요청은 쿠버네티스 Service 를 거치지 않고 자기 자신에게 바로 가기 때문에, readiness 가 503 이어도 막히지 않는다.
반면, 밖에서 Service 로 오는 요청은 readiness 가 503 인 동안 이 Pod 로 오지 않는다.

Runner 가 끝나면 Spring Boot 가 ReadinessState 를 ACCEPTING_TRAFFIC 으로 바꾸고, 그때부터 readiness 가 200 을 응답하고, probe 가 이를 확인하면 트래픽이 들어온다.
로그에서도 Warm-up 이 끝난 다음 1ms 뒤에 ReadinessState 가 바뀌었다.
즉, Warm-up 이 도는 동안은 포트가 열려 있어 자기 API 를 부를 수 있으면서, 밖의 트래픽은 아직 들어오지 않는다.

WebFlux(Netty) 인 경우
Runner 가 끝나야 Ready 가 되는 순서는 같아서, Warm-up 을 두는 자리와 방법은 그대로다.
요청은 Tomcat 대신 Netty 가 받고, DispatcherServlet 대신 WebFilter 와 DispatcherHandler 를 지나간다.
WebClient 를 쓰면 Reactor Netty 가 이벤트 루프와 호스트 이름 리졸버를 첫 요청 때 만들어서 첫 호출이 더 느려진다.
warmup() 으로 이 자원은 미리 만들 수 있지만 연결까지 맺지는 않아서, Warm-up 요청은 그대로 두는 편이 좋다. (Reactor Netty 문서 - Eager Initialization)

2) Runner 에 두는 이유

Warm-up 은 포트가 열려 있으면서 아직 Ready 가 아닌 구간에서 돌아야 하는데, 시작 과정에서 이 조건에 맞는 자리는 Runner 하나다.

  • @PostConstruct : 빈을 만드는 중에 실행돼서 포트가 아직 닫혀 있다. 그래서 자기 API 를 HTTP 로 부를 수 없다.
  • ApplicationRunner : 포트가 열린 뒤에 실행되고, Runner 가 끝나야 Ready 가 된다. 그래서 자기 API 를 부르는 동안 밖의 트래픽은 들어오지 않는다.
  • ApplicationReadyEvent 리스너 : 동기로 처리하면 Runner 와 같지만, @Async 로 넘기면 Ready 가 먼저 되고 Warm-up 은 뒤에서 돌아서 실제 트래픽과 겹친다.

예제 코드에서 요청마다 예외를 잡고 제한 시간을 둔 것도 Runner 에 두었기 때문이다.
Runner 밖으로 예외가 나가면 애플리케이션 시작이 실패하고, 응답이 오지 않는 요청에 묶이면 Runner 가 끝나지 않아 Ready 도 되지 않는다.
그래서 요청마다 예외를 잡아 로그만 남기고, 2초 제한 시간을 둬서 다른 서비스가 느려도 Runner 가 끝나게 했다.

3) API 대신 의존성을 직접 부르기

HTTP 로 자기 API 를 부르지 않고, DB, Redis, 다른 서비스 클라이언트를 Runner 에서 직접 한 번씩 써 두는 방법도 있다.

java
private int warmupDirectly() {
    ...
    this.jdbcClient.sql("select 1").query(Integer.class).single();          // DB
    this.redis.opsForValue().get("warmup");                                  // Redis
    external.get().uri("/stub.json").retrieve().toBodilessEntity();          // 다른 서비스 API
    ...
}

이 방법은 연결은 미리 맺어 두지만, Tomcat 과 DispatcherServlet, 컨트롤러는 지나가지 않는다.

한 번 호출로 충분할까?

아래 환경에서 확인해 보았다.

  • 버전 : Spring Boot 4.1.2, Azul Zulu 25.0.2
  • 로컬 : MySQL, Redis 를 Testcontainers 로 띄우고, 조건마다 서버를 10회 새로 띄워 중앙값을 냈다.
  • 다른 서비스 : 실제 외부 서비스가 아니라, 로컬은 같은 장비에, 배포는 같은 클러스터에 띄운 스텁 서버를 불렀다.
  • 배포 : kind 에서 Pod 마다 CPU 1코어를 주고, 5회 새로 띄워 중앙값을 냈다.
  • 시간 : 로컬의 첫 호출은 앱의 가장 바깥 필터에서 측정한 서버 처리 시간이고, Ready 뒤 몰리는 요청과 배포는 k6 로 측정한 응답 시간이라 네트워크와 대기 시간까지 들어 있다.
예제 코드 보러가기 (클릭)

1) Ready 뒤 첫 호출

API 마다 서버를 새로 띄우고, Ready 가 되고 0.5초 뒤에 보낸 첫 호출의 시간을 비교해 봤다.
테스트할 때에는 의존성이 없는 /hello 도 Warm-up 경로에 넣어 함께 불렀다.

Ready 뒤 첫 호출Warm-up 없음Warm-up 1회직접 1회
/hello6.4ms1.2ms6.4ms
/users/1 (DB)206.1ms3.8ms14.3ms
/products/1 (Redis)264.9ms3.5ms14.4ms
/external (다른 서비스 API)57.8ms3.1ms9.1ms
Ready 까지 걸린 시간2.42초3.10초2.76초

Warm-up 이 없을 때는 의존성이 있는 API 마다 첫 호출이 수십에서 수백 ms 걸렸는데, HTTP 로 1회 불러 두니 모두 4ms 안쪽으로 줄었다.
Redis 는 Warm-up 없이 띄우면 첫 /products/1 이 264.9ms 로 가장 느렸는데, Redis 클라이언트가 첫 명령을 보낼 때 연결을 맺었다.

의존성을 직접 부른 쪽도 첫 호출이 200ms 대에서 10ms 대로 줄어서, 의존성 클라이언트를 미리 한 번 실행하는 것만으로도 큰 지연은 사라졌다.
하지만, HTTP 로 부른 쪽보다는 3~4배 느렸고, 의존성이 없는 /hello 는 Warm-up 없음과 같은 6.4ms 였다.
연결은 준비됐어도 API 경로는 처음 지나가는 것이라, 그 경로의 클래스 로딩 같은 비용이 첫 호출에 남은 것으로 보인다.
Ready 는 직접 부르는 쪽이 0.3초 정도 빨랐지만, 첫 호출을 더 많이 줄이려면 API 를 HTTP 로 부르는 편이 좋다.

2) Ready 뒤 몰리는 요청

실제 배포에서는 새 서버가 Ready 가 되면 요청이 한꺼번에 들어오게 되는데,
이 상황을 재현하기 위해, Ready 뒤 3초 쉬었다가 부하 도구 k6 로 사용자 4명(VU)이 /users/1 을 10초 동안 쉬지 않고 부르게 해 봤다.

Warm-up 없음Warm-up 1회
첫 1초에 처리한 요청초당 1,873건초당 2,630건
첫 1초의 최대 응답 시간230.9ms6.1ms

Warm-up 1회만으로 첫 1초의 최대 응답 시간이 230.9ms 에서 6.1ms 로 줄어 튀는 응답이 사라졌고, 같은 1초 동안 처리한 요청도 1,873건에서 2,630건으로 40% 정도 늘었다.
그래도 몇 초 지나 충분히 빨라진 뒤의 초당 6,639건에는 못 미치는데, Warm-up 1회여도 첫 1초에 JIT 컴파일이 2,500건 넘게 일어난 것이 한 요인으로 보이고,
이 부분은 Warm-up 1회로 없앨 수 있는 대상이 아니다.

3) 여러 번 부르는 경우

한 번보다 여러 번 불러 두면 더 빨라지지 않을까 싶어서, 같은 경로 목록을 1,000회 반복해 불러 보았다.
반복하는 동안 JIT 컴파일이 진행된 덕분인지 11~200번째 호출의 서버 처리 시간은 1회보다 절반 정도로 짧아졌지만(/users/1 기준 1.77ms → 0.78ms), Warm-up 에만 5.3초가 걸려서 Ready 가 3.10초에서 7.73초로 늦어졌다.
첫 호출이 튀는 문제는 1회로 이미 사라지기 때문에, 더 반복하는 것은 Ready 가 늦어지는 것과 맞바꾸는 셈이다.

커넥션 풀도 여러 번 부른다고 달라지지 않는다.
Warm-up 은 요청을 하나씩 보내서 커넥션을 한 번에 하나만 쓰고, 풀에 커넥션이 몇 개 만들어지는지는 HikariCP 의 minimumIdle 설정이 정한다.
기본값은 maximumPoolSize 와 같아서, 첫 연결 뒤에 풀이 그 수까지 커넥션을 채우려고 한다. (HikariCP - Frequently used)

yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10   # 풀의 최대 커넥션 수 (기본값 10)
      minimum-idle: 10        # 놀고 있어도 유지할 커넥션 수 (적지 않으면 maximum-pool-size 와 같다)

요청을 동시에 보내 커넥션을 억지로 늘리면 배포 때마다 Pod 마다 커넥션이 한꺼번에 생겨 DB 에 부담이 되므로, 커넥션 수는 풀 설정으로 정하는 편이 좋다.

배포에서 확인

1) Rolling Update 와 Blue-Green

같은 앱을 두 가지 방식으로 배포하면서, 초당 600건을 계속 보내 응답 시간을 확인해 보았다.

  • Rolling Update : 새 Pod 가 Ready 가 되는 대로 하나씩 트래픽에 넣고, 이전 Pod 를 하나씩 내린다.
  • Blue-Green : 새 Pod 2개가 모두 Ready 가 되고 5초 뒤, Service 를 바꿔 트래픽을 한 번에 넘긴다.

kube-proxy 는 연결 단위로 Pod 를 나누기 때문에, 새 Pod 에도 바로 요청이 가도록 요청마다 새 연결을 맺게 했다.
연결을 재사용하는 환경에서는 새 Pod 로 넘어가는 속도가 달라서 수치도 달라질 수 있다.

Rolling Update 에서는 minReadySeconds 를 늘리면 첫 호출 비용을 피할 수 있을 것처럼 보이는데, 문서를 보면 이 값은 다음 Pod 로 넘어가는 속도만 늦춘다.

Ready 가 된 Pod 는 그 시간 동안에도 트래픽을 받기 때문에, minReadySeconds 만으로는 첫 호출 비용을 피할 수 없고, Warm-up 처럼 Ready 자체를 늦추는 편이 좋다.

2) 배포 중 응답 시간

p99 는 100건 중 가장 느린 1건 정도의 응답 시간이다.

측정Rolling Update, Warm-up 없음Rolling Update, Warm-up 1회Blue-Green, Warm-up 없음Blue-Green, Warm-up 1회
배포 전 p998.2ms3.6ms4.1ms4.4ms
배포 중 p99999.5ms21.4ms783.4ms61.6ms
배포 중 최대 응답 시간2,246.9ms72.4ms1,496.7ms82.9ms
실패한 요청0건0건0건0건

Blue-Green 의 배포 중은 트래픽을 넘긴 뒤 10초 동안이다.
kind 에서는 Pod 하나에 CPU 를 1코어만 줘서 로컬보다 훨씬 느렸는데, Warm-up 없이 배포했더니 배포 중 p99 가 1초 가까이 올라갔다.
실패한 요청은 없었지만, 새 Pod 가 트래픽에 들어오는 동안 응답 지연이 커졌고, Blue-Green 은 트래픽이 한 번에 넘어가서, 넘긴 직후 1초 동안의 p99 가 이미 800ms 였다.

Warm-up 을 1회 넣었을 때는, 배포 중 p99 가 Rolling Update 는 21.4ms, Blue-Green 은 61.6ms 로 내려가서, 1초 가까이 튀던 응답은 사라졌다.
그 대신 새 Pod 의 JVM 시작부터 ApplicationReadyEvent 까지가 7.4초에서 8.9초로 1.5초 정도 늦어졌고, Rolling Update 전체는 17.3초에서 20.0초가 걸렸다.

health 그룹으로 커넥션 풀만 미리 만들기

DB 커넥션 풀만 미리 만들고 싶다면, readiness 를 판정하는 health 그룹에 DB 검사를 넣는 방법도 있다.

yaml
management:
  endpoint:
    health:
      group:
        readiness:
          include: "readinessState,db"

이렇게 하면 쿠버네티스가 readiness 를 확인할 때 DB 검사가 함께 돌면서 커넥션 풀이 만들어진다.

readinessState 를 빼면 안 되는 이유
include 를 직접 적으면, Spring Boot 가 기본으로 만드는 readiness 그룹 대신 적은 항목만 본다.
그래서 db 만 적으면 Runner 가 도는 중에도 readiness 가 200 을 응답해서, Warm-up 이 끝나기 전에 트래픽이 들어올 수 있다.

하지만, DB 가 잠깐 멈추면 모든 Pod 가 한꺼번에 트래픽에서 빠질 수 있어서, Spring Boot 문서도 readiness 에 외부 시스템을 넣을지는 신중하게 정하라고 한다.

또한, DB 연결만 준비할 뿐이라 API 경로의 클래스 로딩이나 Redis, 다른 서비스의 첫 연결은 그대로 첫 호출에 남는다. 이 방법은 따로 측정하지 않았다.

주의할 점

1) 상태를 바꾸는 API 는 넣지 않는다

Warm-up 요청도 실제 요청과 같은 코드를 실행하기 때문에, 조회 API 나 Warm-up 전용 데이터로만 호출하는 것이 좋다.

2) 인증이 필요한 API

인증 필터가 걸린 API 를 그냥 부르면 401 로 필터에서 끝나서, 컨트롤러와 DB 까지 가지 않아 Warm-up 이 되지 않는다.
따라서, 인증이 필요 없는 조회 API 를 고르거나, Warm-up 전용 계정의 토큰을 실어 보내는 편이 좋다.

3) Warm-up 요청도 의존성에 부하를 준다

Warm-up 요청은 자기 서버 안에서 끝나지 않고, 실제 요청처럼 DB, Redis, 다른 서비스까지 간다.
한 번씩만 불러도 Pod 가 많으면 배포할 때마다 (경로 수 x Pod 수) 만큼의 요청이 의존성에 한꺼번에 더해지는데, 같은 경로를 여러 번 반복하면 그만큼 더 커진다.
특히 다른 팀의 서비스나 커넥션 수에 여유가 없는 DB 라면 이 부하가 문제가 될 수 있어서, Warm-up 은 한 번씩만 부르는 편이 좋다.

4) Warm-up 이 실패할 때

Warm-up 요청이 모두 실패해도 Ready 가 되고, 첫 호출 비용을 그대로 안은 채 트래픽을 받게 된다. 따라서 경로를 두 가지로 나눠 다루는 편이 좋다.

경로예시실패할 경우
꼭 미리 불러야 하는 경로자기 DB 를 조회하는 API몇 번 다시 시도해도 실패하면 Runner 에서 예외를 던져 시작을 멈춘다
실패해도 되는 경로다른 팀의 서비스 API로그만 남기고 넘어가서, 다른 서비스가 잠깐 느린 것만으로 배포가 멈추지 않게 한다

실패했을 때 Runner 에서 ReadinessState 를 REFUSING_TRAFFIC 으로 바꿔 Ready 를 막으면 될 것 같지만,
Runner 가 정상으로 끝나면 Spring Boot 가 ACCEPTING_TRAFFIC 으로 다시 바꾼다.
그래서 시작을 멈추려면 Runner 에서 예외를 던지는 편이 좋다.

5) readiness 와 liveness

Warm-up 이 도는 동안 readiness 는 503 을 응답하는데, readiness 실패는 Pod 를 재시작하지 않아서 Warm-up 시간만큼 기다리는 것은 문제가 없다.
liveness 는 Started 뒤에 이미 정상이라 Warm-up 중에도 통과한다.

Warm-up 중에는 readiness 가 503 을 응답해서, probe 가 일찍 확인해도 Service 는 이 Pod 로 트래픽을 보내지 않는다.
Service 를 통한 트래픽은 적어도 아래 두 시점이 지난 뒤에야 들어올 수 있다.

트래픽이 들어오는 시점 ≥ max(readiness 가 200 이 된 시점, readiness probe 가 처음 실행되는 시점)

그래서 initialDelaySeconds 를 Warm-up 시간에 맞춰 길게 잡으면, 준비가 끝난 Pod 도 첫 확인을 기다리게 된다.
initialDelaySeconds 는 늘릴 필요가 없고, Ready 를 빨리 알아차리려면 확인 주기(periodSeconds)를 짧게 두는 편이 좋은데, 너무 짧으면 확인 요청이 그만큼 늘어나서 서비스에 맞게 정하는 편이 좋다. (Kubernetes 문서 - Configure Probes)

설정은 아래와 같은 형태로, 값은 예시다.

yaml
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  periodSeconds: 2   # 확인 주기 예시 (기본값 10)

정리

요약
✔ Ready 여도 첫 연결과 클래스 로딩이 남아 있어서, Ready 뒤 첫 호출이 느릴 수 있다
✔ ApplicationRunner 에서 첫 호출이 느린 경로를 HTTP 로 한 번씩 불러 두면, 이 비용을 Ready 전으로 옮길 수 있다
✔ 한 번만 불러도 /users/1 의 첫 호출이 206.1ms 에서 3.8ms 로 줄었고, 배포 중 p99 도 1초 가까이에서 수십 ms 로 내려갔다
✔ 그 대신 Ready 가 1초 안팎 늦어지는데, Warm-up 중에는 readiness 가 503 이라서 probe 는 확인 주기를 짧게 두는 편이 좋다
✔ Ready 가 조금 늦어지는 것을 받아들일 수 있다면, 배포 직후 튀는 응답을 줄이는 데 Warm-up 한 번이면 충분하다
